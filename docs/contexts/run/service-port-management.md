# 本地服务端口治理规划

## 文档地位

本文记录 cleancode 在多个项目、多个分支工作区和多个终端服务并行运行时的端口治理方向、当前实现基线、阶段计划与进度。

本文是规划与进度记录，不是当前功能清单、稳定产品契约、正式 Spec 或已经确认的实现 Plan。尚未实现的内容不得据此表述为当前能力；进入生产实现前，仍须按[开发协作规范](../../engineering/development.md)完成 Large Change 的 Spec、可行性检查、Plan、TDD 和验证流程。

当前能力以[终端会话生命周期](terminal-session.md)、[终端依赖工作流](terminal-workflow.md)、[积木图模型](../block-graph/block-graph.md)、代码和自动化测试为准。用户可见的未实现方向由 [UI 路线图](../../product/ui-roadmap.md)索引；方向完成并形成稳定约束后，再迁入 [UI 契约](../../product/ui.md)和相应上下文专文。

## 背景与问题

Git worktree 隔离文件目录和 Git 分支，但同一台主机上的本地进程仍共享 TCP/UDP 端口空间。因此以下场景属于同一类运行时资源冲突：

- 不同项目都使用框架默认端口，例如两个项目同时监听 `3000` 或 `5173`。
- 同一项目的多个 worktree 同时启动相同开发服务。
- 已退出 cleancode 界面但仍存活的子进程继续占用端口。
- cleancode 管理的服务与外部终端、IDE、容器或系统服务使用同一端口。

当前固定 TCP 就绪探测只证明“某个进程正在监听该端口”，不能证明监听者是本次启动的服务。若旧服务已经占用配置端口，新运行可能在自身绑定失败前短暂获得错误的就绪信号。

同时，动态端口并非对所有项目都透明：不同框架可能通过环境变量、命令参数、配置文件或运行时 API 接收端口；OAuth 回调、CORS、webhook、移动端或外部工具还可能要求固定端口。系统不能靠猜测或改写项目文件解决这些差异。

## 目标

规划方向希望达到以下体验：

- 多个项目和多个 worktree 可以并行启动使用相同默认端口的服务。
- 普通场景不要求用户手工维护工作区端口表。
- 需要固定端口的项目可以明确选择固定语义，并在冲突时获得可操作反馈。
- 用户看到的是服务身份和实际访问地址，而不只是裸端口号。
- 系统只允许停止能够确认属于 cleancode 的受管进程，不自动终止外部进程。
- 服务就绪、下游放行和“打开服务”都使用本次运行的实际端点。
- 停止、失败、工作区归档、项目移除和应用退出后，运行资源能够按清晰生命周期释放。

## 非目标

基础阶段不计划：

- 为所有框架自动推断端口配置方式或修改项目源码、`.env`、CORS 和 OAuth 配置。
- 自动杀死未知监听进程，或根据未验证的陈旧 PID 执行破坏性操作。
- 仅为解决本地端口冲突而强制用户采用 Docker、Dev Container、虚拟机或远程环境。
- 在基础端口分配完成前同时引入完整反向代理、HTTPS 证书、本地域名和跨节点产物传递。
- 把一次实际分配端口持久化为下一次运行必须复用的业务事实。

## 统一语言候选

以下术语用于后续 Spec 对齐，尚未成为已实现领域模型：

| 术语       | 候选含义                                                         |
| ---------- | ---------------------------------------------------------------- |
| 端口策略   | 服务对本机监听端口的意图，候选值为 `fixed`、`preferred`、`auto`  |
| 固定端口   | 端口不可改变；冲突时停止启动并等待用户处理                       |
| 首选端口   | 优先使用指定端口，冲突时允许分配其他端口                         |
| 自动端口   | 不要求指定端口，由运行时分配可用端口                             |
| 端口绑定   | 把实际端口传给目标服务的方式，例如环境变量、命令参数或服务自报告 |
| 端口租约   | Run 在一次运行期间拥有的易失端口分配记录                         |
| 实际端点   | 本次服务运行最终使用的协议、主机、端口和可选 URL                 |
| 监听者     | 当前占用候选端口的操作系统进程或服务实例                         |
| 受管监听者 | 能被当前 cleancode 运行身份可靠关联和停止的监听者                |
| 外部监听者 | 无法证明属于当前 cleancode 运行身份的监听者                      |

## 状态所有权候选

端口治理计划沿用现有限界上下文，不新增独立上下文：

| 事实或能力                     | 候选 owner         | 说明                                                          |
| ------------------------------ | ------------------ | ------------------------------------------------------------- |
| 项目、工作区和目录身份         | Project            | 继续由 Project 提供稳定作用域，不让 Run 读取 Project 内部模型 |
| 端口策略和端口绑定配置         | BlockGraph         | 作为服务执行意图随终端积木和工作区持久化                      |
| 不可变工作流计划               | BlockGraph         | 通过 Run 拥有的 `TerminalWorkflowPlanPort` 提供 DTO           |
| 端口租约、实际端点和冲突重试   | Run                | 属于一次运行的易失状态，不反写 BlockGraph                     |
| 进程启动、端口分配和监听者检查 | Run infrastructure | 通过 Run 应用层端口实现本机能力                               |
| 冲突提示、实际地址和操作入口   | Presentation       | 由运行快照和结构化错误派生，不成为事实来源                    |
| IPC 注册和依赖装配             | Platform           | 只连接用例、端口和适配器，不拥有端口策略                      |

工作区归档、主工作区切换分支或项目移除是否需要由 Project 通过调用方拥有的 `WorkspaceRunLifecyclePort` 排空 Run 资源，将在正式 Spec 中确认。若新增该协作，须同步更新[上下文地图](../../engineering/context-map.md)以及 Project、Run 的用例和契约测试。

## 候选不变量

正式 Spec 需要至少确认以下不变量：

1. 同一时刻，一个受管端口租约只归属于一个精确运行身份；运行身份至少包含项目、工作区、终端服务和运行 ID。
2. `fixed` 端口被占用时不静默回退；`preferred` 或 `auto` 获得的新端口必须成为启动、就绪、事件和界面共同使用的唯一实际端点。
3. 未证明属于 cleancode 的监听者不会被自动终止；停止或失败只释放本次运行拥有的进程、探测器、计时器和端口租约。
4. TCP 可连接本身不足以证明当前服务就绪；就绪判断还需要关联本次运行与实际端点，并确认受管进程没有提前退出。
5. 端口分配属于易失运行状态；应用重启后重新分配，不把陈旧租约或 PID 当作可恢复事实。

## 端口策略候选

### `preferred`

计划作为普通本地开发服务的默认策略：

- 先尝试用户或框架熟悉的端口。
- 冲突时从受控范围或操作系统动态分配其他端口。
- 成功后以低噪声方式说明实际地址，不要求用户确认每次自动回退。
- 如果项目无法接受动态端口，用户改用 `fixed`。

### `fixed`

适用于外部回调、固定 CORS、硬编码客户端或其他严格依赖：

- 端口空闲时按原值启动。
- 端口冲突时不启动，也不自动递增。
- 界面说明监听者身份和影响，并让用户选择停止受管服务、查看外部进程详情、修改配置或取消。

### `auto`

适用于测试服务、临时预览和内部依赖：

- 优先让目标服务监听端口 `0` 并在成功监听后报告实际端口。
- 目标服务不支持端口 `0` 时，使用受管分配与有界重试；不能把“先检查空闲再释放端口”当作无竞争保证。
- 实际端点通过运行快照和事件提供给表现层及后续依赖。

## 端口绑定候选

任意 Shell 命令没有统一的端口参数。基础阶段计划只支持用户或项目显式声明的结构化绑定，不根据命令文本猜测：

- 环境变量，例如把实际端口注入 `PORT`。
- 命令参数模板，例如把实际端口填入 `--port {port}`。
- 服务自报告，例如服务监听端口 `0` 后通过结构化握手返回实际端点。
- 无注入，适用于已经在启动命令或外部配置中固定端口的服务。

环境变量名称、参数模板的安全边界、Shell 转义、Windows/macOS/Linux 差异和向后兼容格式需要先完成可行性检查。系统不会在未授权时写入项目配置文件。

## 冲突交互候选

计划采用所有权感知的差异化反馈：

- `preferred` 或 `auto` 自动回退成功：使用应用通知短暂说明“首选端口被占用，已改用实际地址”，终端节点保留可发现的打开/复制入口。
- `fixed` 被受管监听者占用：展示项目、工作区和服务身份，并提供“打开已有服务”“停止已有服务并重试”“修改配置”“取消”。
- `fixed` 被外部监听者占用：展示可安全获得的进程名称、PID 和诊断信息，只提供“查看详情”“修改配置”“取消”；不默认提供终止动作。
- 无法判断监听者身份：按外部监听者处理，不把不确定性解释为 cleancode 所有权。

正常启动保持静默；只有自动改用端口、固定端口冲突、分配失败或资源清理失败需要占用用户注意力。通知关闭不改变运行状态，实际端点仍由终端节点或运行详情表达。

## 验证计划

正式实现预计按测试金字塔覆盖：

- Unit：端口策略校验、租约状态迁移、完整运行身份、冲突决策、重复释放和错误映射。
- Integration：真实端口竞争、动态端口、并行项目/worktree、PTY 环境/参数注入、进程提前退出、停止后释放和有界重试。
- Contract：BlockGraph 配置、Run IPC、运行事件、实际端点和结构化冲突信息的输入输出。
- Presentation unit：默认策略、固定端口冲突、自动回退通知、受管/外部监听者动作和可访问性。
- E2E：低层测试完成后，再评估一条“两个工作区请求相同首选端口，均成功启动并获得不同实际端点”的关键用户路径。边界和错误分支继续留在低层测试。

所有 TCP 和 PTY 测试使用测试进程与操作系统分配的临时端口，不依赖用户环境中的固定端口；清理必须等待进程退出并保留失败诊断。

## 主要风险与待确认问题

- 普通终端会话当前以 `workspaceName + terminalBlockId` 识别槽位；是否统一加入项目作用域，需要与现有工作区切换和会话迁移一起确认。
- 任意 Shell 命令无法通用地接收动态端口；首批支持哪些绑定方式需要可行性原型。
- 端口检查与子进程真正监听之间存在竞争；跨平台预留、句柄交接或失败重试的边界需要验证。
- 只检查 TCP 连接无法证明监听者所有权；进程树关联、启动握手和健康标记需要选择可移植方案。
- 应用崩溃后可能留下子进程；持久化 PID 存在复用风险，重启时不能据此直接终止进程。
- 多个 cleancode 应用进程同时运行时，进程内租约表不足以全局协调；操作系统动态分配和外部监听者识别需要覆盖该场景。
- 稳定本地域名或代理需要处理 HMR/WebSocket、Host 校验、CORS、Cookie、HTTPS 和安全暴露范围。
- 默认监听地址计划保持为 `127.0.0.1`；任何 `0.0.0.0` 或公网转发都需要显式用户意图和独立安全评估。

## 成熟做法参考

- [Node.js `net` 文档](https://nodejs.org/api/net.html)：监听端口 `0` 时由操作系统分配未使用端口，并可在监听后读取实际端口。
- [Vite Server Options](https://vite.dev/config/server-options)：默认端口占用时尝试下一可用端口，`strictPort` 用于固定端口失败语义。
- [Docker Compose 网络](https://docs.docker.com/compose/how-tos/networking/)：项目网络内使用稳定服务名，宿主机端口可以独立映射。
- [Docker Compose 服务端口](https://docs.docker.com/reference/compose-file/services/)：只声明容器端口时可由运行时动态分配宿主机端口。
- [VS Code Remote SSH 端口转发](https://code.visualstudio.com/docs/remote/ssh)：本地目标端口冲突时映射到其他端口，并向用户展示最终地址。

这些参考只证明成熟模式和技术可行方向，不自动决定 cleancode 的领域模型、交互语义或依赖选择。
