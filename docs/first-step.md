# 第一步总览

## 文档地位

本文定义 cleancode 第一阶段的整体方向。

本文不是 Spec，不替代 Spec，也不替代 Plan。正式功能开发仍必须遵守 [AI 协作流程](ai-workflow.md)。

本文不重新定义架构规则。架构规则、限界上下文、分层规则、依赖方向和事实来源以 [架构文档](architecture.md) 为唯一事实来源。

第一版功能阶段的 UI 布局和用户可见功能以 [UI 规范](ui.md) 为准。

## 第一阶段定位

第一阶段不是只搭一个项目目录，也不是只画一个静态积木图，而是交付一个可以被用户真实使用的最小工作台闭环。

第一阶段名称：

```txt
本地项目工作台、最小积木图与可用终端积木闭环
```

第一阶段完成后，用户应该已经能感受到 cleancode 的核心产品形态：在一个本地项目中，通过工作台查看和编辑一个可保存的积木图，并在图中的终端积木里像平常使用终端一样执行命令。

## 第一阶段目标

第一阶段目标是建立 cleancode 的第一个可用业务闭环：

```txt
启动桌面应用
  ↓
添加本地项目
  ↓
进入 main 分支工作区
  ↓
进入项目工作台
  ↓
创建或打开 main 工作面的默认积木图
  ↓
在画布上创建、查看、移动、删除终端积木
  ↓
保存积木图
  ↓
在终端积木中启动交互式终端
  ↓
像普通终端一样输入命令并查看输出
  ↓
关闭后再次启动应用并恢复同一个项目、积木图和终端积木
```

这个闭环同时解决三个问题：

- 用户的工作保存在哪里。
- 用户当前处于哪个项目和分支工作区。
- 用户最核心的积木图如何被创建、编辑和再次恢复。
- 第一个积木类型如何提供真实可用的本地能力。

第一阶段完成后，项目应具备继续开发运行期 Agent、图执行引擎、插件能力和复杂积木类型的稳定基础。

## 为什么扩大第一步

只创建本地项目目录过于偏底层，用户无法感知 cleancode 的积木式工作方式。

第一阶段必须让用户看到“项目承载积木图”的完整关系：

- 本地项目目录提供本地归属和持久化边界。
- 分支工作区提供未来多 Agent 并行开发的工作面边界。
- 积木图提供产品核心编辑对象。
- 终端积木提供第一个真实可用的积木能力。
- 工作台把项目、积木图和终端能力组织到同一个用户入口。

终端积木适合作为第一个积木类型，因为它是本地开发工作流中最基础、最直观、最可验证的能力。

这样后续接入运行期 Agent 时，Agent 操作的对象已经存在明确的项目归属、图结构事实来源、终端运行边界和审计边界。

## 第一阶段范围

第一阶段只关注本地单用户项目、最小积木图编辑和可交互终端积木。

必须覆盖：

- 创建一个 cleancode 本地项目目录。
- 识别一个目录是否是 cleancode 本地项目目录。
- 读取项目元数据。
- 展示第一版项目侧边栏。
- 提供添加项目入口。
- 在项目下展示 `main` 分支工作区。
- 将 `main` 作为默认工作区，不再提供并列的“默认工作区”。
- 在未初始化 Git 时，将 `main` 作为未绑定真实 Git 分支的逻辑分支工作区。
- 进入项目工作台。
- 创建 main 工作面的默认积木图。
- 读取 main 工作面的默认积木图。
- 展示第一版积木画布。
- 展示第一版小地图。
- 在默认积木图中创建终端积木。
- 在默认积木图中移动终端积木。
- 在默认积木图中删除终端积木。
- 保存默认积木图。
- 在终端积木中启动本地 shell。
- 在终端积木中输入命令。
- 在终端积木中查看标准输出和标准错误。
- 终端积木默认工作目录必须是当前分支工作区对应的本地目录。
- 可以像普通终端一样通过 Ctrl+C 停止当前命令。
- 可以重新启动终端会话。
- 关闭应用时必须结束终端会话。
- 关闭后再次启动应用时恢复同一个项目和积木图。

可以覆盖，但必须保持最小：

- 展示终端积木的名称和简单描述。
- 配置终端积木的启动 shell。
- 展示终端会话状态，例如未启动、运行中、已退出。

可以延后：

- 多项目窗口。
- 最近项目列表。
- 项目模板。
- 创建真实 Git 分支。
- 删除真实 Git 分支。
- 切换真实 Git 分支。
- Git 合并、变基和冲突解决。
- Git worktree 管理。
- 云同步。
- 多人协作。
- 权限系统。
- 插件市场。
- 运行期 Agent 真正创建、修改或运行积木。
- 完整图执行引擎。
- 复杂端口类型系统。
- 完整积木属性面板。
- 多终端标签页。
- 终端分屏。
- 远程终端。

## 非目标

第一阶段不实现完整积木编辑器。

第一阶段不实现完整图执行引擎。

第一阶段只实现终端积木的交互式 PTY 会话，不实现通用积木运行编排。

第一阶段不接入真实 AI CLI。

第一阶段不实现 MCP 或 JSON-RPC 工具协议。

第一阶段不实现插件加载和插件市场。

第一阶段不实现完整 SQLite 业务 schema。

第一阶段不引入跨项目同步、账号体系或远程服务。

第一阶段不实现文件树、源码搜索、Git 历史面板或完整 IDE 功能。

第一阶段不实现真实 Git 分支创建、切换、删除、合并、变基或冲突解决。

第一阶段不实现复杂自动布局、版本迁移或多人协作冲突合并。

第一阶段不保证关闭应用后恢复正在运行的终端进程。

第一阶段不持久化完整终端滚屏历史。是否保存命令历史由用户 shell 自己决定。

## 涉及限界上下文

第一阶段涉及三个主上下文：

- 项目上下文。
- 积木图上下文。
- 运行上下文。

项目上下文负责：

- 项目身份。
- 本地项目目录。
- 分支工作区身份。
- 分支工作区名称。
- 分支工作区 Git 绑定。
- 分支工作区对应的本地目录。
- 项目元数据。
- 项目文件引用。
- 项目打开与关闭。

积木图上下文负责：

- 积木图身份。
- 终端积木类型。
- 终端积木位置。
- 终端积木连接。
- 图结构保存与读取。
- 图结构最小校验。

运行上下文负责：

- 终端会话身份。
- 终端会话生命周期。
- 终端输入。
- 终端输出。
- 终端退出状态。
- 终端会话错误。

项目上下文不得接管积木图内部结构。

积木图上下文不得接管项目路径、项目元数据和项目打开流程。

积木图上下文不得接管 PTY 进程、终端输入输出流或终端会话生命周期。

运行上下文不得接管项目元数据、项目路径选择或积木图结构规则。

Agent 上下文和插件上下文不进入第一阶段实现范围。

## 第一阶段业务事实

项目上下文拥有以下业务事实：

- 一个项目必须有稳定身份。
- 一个项目必须有本地项目目录。
- 一个项目必须有可读取的项目元数据。
- 一个本地项目目录必须能被再次识别和打开。
- 一个项目必须至少暴露一个名为 `main` 的分支工作区。
- `main` 分支工作区就是默认工作区，系统不得创建另一个并列的默认工作区。
- 一个分支工作区可以绑定真实 Git 分支，也可以在 Git 未初始化时保持未绑定。
- 一个分支工作区必须能解析到一个本地目录。
- 项目元数据是项目识别和打开的事实来源。

积木图上下文拥有以下业务事实：

- 一个积木图必须有稳定身份。
- 一个积木图归属于一个项目。
- 第一阶段默认积木图归属于项目内的 `main` 分支工作区。
- 一个积木图可以包含零个或多个终端积木。
- 一个终端积木必须有稳定身份、类型和位置。
- 图结构是积木创建、移动、删除和连接规则的事实来源。
- 图结构必须可以保存后再次读取。

运行上下文拥有以下业务事实：

- 一个终端会话必须归属于一个终端积木。
- 一个终端会话必须归属于当前分支工作区。
- 一个终端会话必须有明确生命周期：未启动、运行中、已退出或失败。
- 终端输入必须进入对应终端会话。
- 终端输出必须从对应终端会话产生。
- 停止当前命令必须向对应 PTY 发送 Ctrl+C，并保持 shell 会话可继续输入。
- 删除、重启终端积木或关闭应用时，必须终止对应 PTY 进程。

项目上下文不拥有以下事实：

- 积木图内部结构。
- 积木连接规则。
- 积木运行生命周期。
- Agent 操作历史。
- 插件能力声明。
- UI 临时布局状态。

积木图上下文不拥有以下事实：

- 项目目录选择。
- 项目元数据格式。
- 文件系统写入细节。
- 运行期 Agent 工具协议。
- 终端输入输出流。
- PTY 进程生命周期。
- 终端退出状态。

运行上下文不拥有以下事实：

- 项目元数据格式。
- 积木图持久化格式。
- 终端积木在画布上的位置。
- 终端积木是否可以连接到其他积木。

## 第一阶段推荐 Spec 拆分

第一阶段不应压成一个过大的 Spec。

推荐拆为以下 Spec 顺序推进：

```txt
Spec 1：创建和打开本地项目工作台
  ↓
Spec 2：创建和保存默认积木图
  ↓
Spec 3：创建和编辑终端积木
  ↓
Spec 4：使用终端积木
```

Spec 1 只回答“用户如何添加一个可再次进入的 cleancode 项目工作台，并进入 `main` 分支工作区”。

Spec 2 只回答“`main` 工作面内默认积木图如何创建、保存和再次读取”。

Spec 3 只回答“用户如何在默认积木图中创建、移动、删除终端积木，以及是否支持最小连接”。

Spec 4 只回答“用户如何在终端积木中启动、输入、查看输出、停止和重启交互式终端会话”。

每个 Spec 都必须经过用户确认后，才能进入对应 Plan。

## 第一阶段验收标准

第一阶段完成时，至少满足以下验收标准：

- 用户可以从桌面应用添加一个本地项目目录。
- 用户再次启动桌面应用后可以恢复已添加项目。
- 系统可以在 cleancode 应用状态目录内写入和读取项目元数据。
- 左侧边栏提供添加项目入口。
- 左侧边栏在项目下显示 `main` 分支工作区。
- 未初始化 Git 的项目也显示 `main` 分支工作区。
- 系统不显示并列的“默认工作区”。
- 应用进入项目工作台后能展示当前项目身份。
- 应用进入项目工作台后能展示当前分支工作区身份。
- 项目工作台能创建或打开默认积木图。
- 项目工作台使用 C 版画布优先布局。
- 项目工作台不展示文件树。
- 项目工作台左上角展示小地图。
- 用户可以在默认积木图中创建终端积木。
- 用户可以移动终端积木。
- 用户可以删除终端积木。
- 系统可以保存默认积木图。
- 用户关闭应用后再次启动应用，默认积木图和终端积木仍然存在。
- 用户可以在终端积木中启动本地 shell。
- 终端积木可以接收键盘输入。
- 终端积木可以显示命令输出和错误输出。
- 终端积木的默认工作目录是当前分支工作区对应的本地目录。
- 用户可以通过 Ctrl+C 停止当前运行的命令。
- 用户可以重启终端会话。
- 应用关闭时必须结束仍在运行的终端会话。
- 生产行为有测试覆盖。
- `pnpm pre-commit` 通过。
- 涉及构建或 Electron 入口变化时，`pnpm build` 通过。

## 设计约束

第一阶段必须保持高内聚低耦合。

项目上下文只处理项目事实，不承载积木图、运行、Agent 或插件规则。

分支工作区属于项目上下文，不能被表现层当作纯 UI 状态，也不能被运行上下文或积木图上下文接管。

积木图上下文只处理图结构事实，不承载项目打开、文件系统细节、终端运行、Agent 或插件规则。

运行上下文只处理终端会话和后续运行事实，不承载图结构编辑、项目元数据或 UI 状态。

表现层只能通过应用层用例创建项目、修改积木图和控制终端会话。

文件系统读写必须通过应用层端口和基础设施适配器完成。

PTY 进程必须通过应用层端口和基础设施适配器完成。

Electron 目录选择、窗口生命周期和依赖装配必须留在 `platform` 内。

任何项目元数据格式只能有一个事实来源。

任何积木图持久化格式只能有一个事实来源。

第一阶段可以使用文件系统保存项目元数据和默认积木图，但不得把文件格式解析散落到表现层、平台层或领域层。

第一阶段可以使用 `node-pty` 实现终端能力，但 `node-pty` 只能出现在基础设施适配器中。

第一阶段可以使用 `xterm.js` 展示终端，但 `xterm.js` 只能出现在表现层中。

## 后续演进

第一阶段完成后，推荐进入第二阶段：

```txt
运行期 Agent 操作终端积木和修改积木图
```

第二阶段主上下文应引入 Agent 上下文，并通过应用层用例让运行期 Agent 操作已有终端积木和积木图。

运行期 Agent 不得直接修改积木图文件、React 状态、领域对象或 PTY 进程。
