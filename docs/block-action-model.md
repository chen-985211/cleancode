# 积木动作模型

## 文档地位

本文记录扩展多种积木时，积木按钮、批量操作和组合动作的统一规划。

本文不替代 [架构文档](architecture.md) 和 [UI 契约](ui.md)。架构边界、依赖方向和事实来源仍以架构文档为准；终端积木与终端组合的稳定用户可见语义仍以 UI 契约为准。未实现方向只具有规划意义，不得推导为当前能力。

## 背景

当前工作台已经有终端积木和终端组合。终端积木提供启动命令、停止当前命令、编辑、删除和空会话重开等动作；终端组合提供对应的成员批量动作。具体按钮排列属于可演进的表现细节。

随着未来出现 Agent 积木、预览积木、HTTP 请求积木、测试积木等新类型，如果按钮只按图标或位置复用，就可能出现“看起来是服务于终端积木的动作，却错误影响 Agent 积木”的问题。

因此，积木动作不能只定义“做什么”，还必须定义“作用在谁身上”。

## 核心原则

积木动作必须由以下信息共同定义：

```txt
动作 = 功能意图 + 作用对象 + 可作用的积木类型 + 执行入口 + 用户可见文案
```

其中：

| 概念             | 含义                             | 示例                                     |
| ---------------- | -------------------------------- | ---------------------------------------- |
| 功能意图         | 动作想完成的业务目标             | 运行配置动作、停止当前执行、重启运行环境 |
| 作用对象         | 动作实际影响的对象集合           | 单个终端积木、终端组合内全部终端成员     |
| 可作用的积木类型 | 该动作允许作用于哪些积木类型     | terminal、agent、preview                 |
| 执行入口         | 动作最终进入哪个应用层用例或端口 | 启动终端会话、写入启动命令、停止 PTY     |
| 用户可见文案     | UI 上展示给用户的名字和 tooltip  | 启动命令、重开空终端会话                 |

任何动作如果缺少明确作用对象，就不应该出现在 UI 中。

## 三类状态

设计积木动作时，必须区分三类状态：

| 状态类别 | 含义                         | 示例                                         |
| -------- | ---------------------------- | -------------------------------------------- |
| 配置     | 持久化在积木里的可复用设置   | 启动命令、请求 URL、测试脚本、Agent 任务模板 |
| 当前执行 | 正在运行、可停止或取消的工作 | dev server、HTTP 请求、测试进程、Agent 任务  |
| 运行环境 | 承载执行的会话或资源         | 终端 shell、浏览器预览会话、Agent 会话       |

因此，“重新运行配置动作”和“重启运行环境”是两个不同能力。

例如终端积木中：

| 动作           | 状态类别        | 行为                                 |
| -------------- | --------------- | ------------------------------------ |
| 启动命令       | 配置 + 当前执行 | 替换旧终端会话并执行已配置启动命令   |
| 停止当前命令   | 当前执行        | 向当前终端会话发送 Ctrl+C            |
| 重开空终端会话 | 运行环境        | 替换为新的空终端会话，不执行启动命令 |

## 动作分类

所有积木动作应优先归入以下能力分类：

| 能力分类     | 说明                     | 终端积木示例       | 未来积木示例                            |
| ------------ | ------------------------ | ------------------ | --------------------------------------- |
| 运行配置动作 | 执行积木保存的主要配置   | 启动命令           | 发送请求、运行测试、开始 Agent 任务     |
| 停止当前执行 | 停止或取消正在运行的工作 | 停止当前命令       | 取消请求、停止测试、停止 Agent 任务     |
| 重启运行环境 | 重建承载执行的会话或资源 | 重开空终端会话     | 刷新预览会话、重启 Agent 会话           |
| 编辑配置     | 修改积木持久化配置       | 编辑终端信息       | 编辑请求、编辑测试参数、编辑 Agent 任务 |
| 结构管理     | 修改积木或组合结构       | 删除终端、移出组合 | 删除积木、解散组合                      |

按钮图标和位置可以相似，但动作只有在功能意图、作用对象和可作用类型都一致时，才属于同一类。

## 作用对象模型

作用对象必须显式建模，避免动作误伤不相关积木。

| 作用对象   | 含义                               | 示例                     |
| ---------- | ---------------------------------- | ------------------------ |
| 单个积木   | 只作用于一个具体积木实例           | 单个终端的启动命令       |
| 类型化组合 | 作用于组合内符合类型约束的成员     | 终端组合启动所有终端命令 |
| 选中集合   | 作用于当前选中的若干积木           | 未来批量删除、批量移动   |
| 工作流编排 | 作用于有执行顺序和依赖关系的积木图 | 运行当前终端依赖工作流   |

原则：

1. 单个积木动作只作用于该积木本身。
2. 类型化组合动作只作用于组合声明的成员集合。
3. 混合选择不能直接展示某个具体类型的动作，除非该动作对所有选中类型都有一致语义。
4. 工作流编排不能复用简单组合的按钮语义，必须有自己的运行规则和错误恢复策略。

## 类型化组合

终端组合应被视为类型化组合，而不是普通视觉分组。

```txt
TerminalGroup
  members: terminal only
  actions:
    - 启动组合命令 -> 所有终端成员
    - 停止全部当前命令 -> 所有终端成员
    - 重开组合终端会话 -> 所有终端成员
```

类型化组合的价值是把同类积木打包成一个更高层的操作对象。它可以拥有批量动作，但批量动作必须明确作用范围。

未来可以存在多种组合：

| 组合类型   | 成员类型             | 目的                | 是否有专属运行动作 |
| ---------- | -------------------- | ------------------- | ------------------ |
| 视觉分组   | 任意积木             | 整理画布、一起移动  | 通常没有           |
| 终端组合   | 只允许终端积木       | 管理一组开发命令    | 有                 |
| Agent 组合 | 只允许 Agent 积木    | 管理一组 Agent 任务 | 可有               |
| 工作流组合 | 多种积木，带依赖规则 | 编排跨类型执行流程  | 必须单独定义       |

不要把终端组合泛化成“所有积木组合”。如果未来需要 Terminal + Agent + Preview 的混合运行，它更接近工作流编排，而不是终端组合。

## 当前终端动作映射

| UI 文案          | 功能意图         | 作用对象               | 可作用类型     |
| ---------------- | ---------------- | ---------------------- | -------------- |
| 启动命令         | 运行配置动作     | 单个终端积木           | terminal       |
| 停止当前命令     | 停止当前执行     | 单个终端积木           | terminal       |
| 重开空终端会话   | 重启运行环境     | 单个终端积木           | terminal       |
| 从此处运行流程   | 运行依赖子图     | 当前终端及其后代       | terminal       |
| 编辑终端信息     | 编辑配置         | 单个终端积木           | terminal       |
| 删除终端         | 结构管理         | 单个终端积木           | terminal       |
| 停止流程         | 停止依赖图       | 当前活动终端工作流     | terminal       |
| 启动组合命令     | 批量运行配置动作 | 终端组合内全部终端成员 | terminal group |
| 停止全部当前命令 | 批量停止当前执行 | 终端组合内全部终端成员 | terminal group |
| 重开组合终端会话 | 批量重启运行环境 | 终端组合内全部终端成员 | terminal group |

## 未来 Agent 积木示例

Agent 积木不应该继承终端积木的动作文案或运行语义。它应该声明自己的动作：

| UI 文案         | 功能意图     | 作用对象        | 可作用类型 |
| --------------- | ------------ | --------------- | ---------- |
| 开始任务        | 运行配置动作 | 单个 Agent 积木 | agent      |
| 停止任务        | 停止当前执行 | 单个 Agent 积木 | agent      |
| 重启 Agent 会话 | 重启运行环境 | 单个 Agent 积木 | agent      |
| 编辑任务        | 编辑配置     | 单个 Agent 积木 | agent      |

即使 Agent 动作和终端动作使用相同图标，也不能默认复用同一个处理函数。只有在应用层用例和作用对象都明确一致时，才能抽象为共享动作能力。

## UI 渲染规则

UI 不应该维护一份所有积木共享的固定按钮列表。更稳的方向是：

```txt
BlockType 声明支持的动作
GroupType 声明允许的成员类型和组合动作
UI 根据动作声明渲染按钮
点击动作后进入该动作声明绑定的用例入口
```

按钮展示规则：

1. 只展示当前积木类型声明支持的动作。
2. 组合节点只展示该组合类型声明支持的组合动作。
3. 动作文案必须体现作用对象，尤其是组合动作。
4. Tooltip 必须补足破坏性语义，例如“重开空终端会话不会执行启动命令”。
5. 对混合选择，默认只展示所有选中类型共同支持且语义一致的动作。

## 架构边界

动作模型必须遵守 DDD + Clean Architecture：

1. 表现层只负责展示动作、收集点击和临时 UI 状态。
2. 业务动作必须进入所属上下文的应用层用例。
3. 基础设施能力必须通过应用层端口访问，例如 PTY、Agent CLI、浏览器预览会话。
4. 积木图结构事实来源属于 `BlockGraph` 聚合。
5. 当前运行生命周期事实来源属于运行上下文。
6. Agent 会话、任务和审计事实来源属于 Agent 上下文。

当前“从此处运行流程”跨越 `BlockGraph` 与 `Run` 上下文，由独立应用服务通过稳定端口取得不可变计划并协调运行，不得让 UI 组件直接调用多个上下文内部实现。

混合 Terminal、Agent、Preview 等多种积木类型的工作流仍属于后续规划；当前实现只接受终端依赖图。

## 设计不变量

1. 动作必须明确作用对象；没有作用对象的动作不能执行。
2. 类型化组合的批量动作只能影响组合声明允许的成员类型。
3. 视觉分组不能自动获得类型化组合的运行能力。
4. 运行配置动作、停止当前执行、重启运行环境必须保持语义区分。
5. UI 文案、tooltip 和测试名称必须使用同一套统一语言。

## 后续演进建议

后续实现更多积木类型时，可以逐步引入动作声明结构：

```txt
BlockActionDescriptor
  id
  intent
  targetScope
  supportedBlockTypes
  label
  tooltip
  icon
  invoke
```

组合动作可以使用类似结构：

```txt
GroupActionDescriptor
  id
  intent
  targetMemberTypes
  label
  tooltip
  invokeForMembers
```

这些声明不必一开始做成复杂框架。第一步可以先让终端积木和终端组合的动作命名、作用对象、测试断言全部显式化，避免未来新增 Agent 积木时复制终端按钮造成语义污染。
