# UI 契约

## 文档地位

本文定义 cleancode 工作台长期有效的用户界面契约，包括信息架构、对象语义、关键交互不变量、状态反馈和视觉原则。

本文不是当前界面的截图说明、组件实现清单、版本验收记录或产品路线图。具体 DOM、CSS、图标、按钮排列和临时文案由当前实现与行为测试证明；尚未确认或尚未交付的方向统一记录在 [UI 路线图](ui-roadmap.md)，不得从路线图推导当前功能已经存在。

本文不重新定义架构规则、限界上下文、依赖方向或业务事实来源。相关规则以 [架构文档](../engineering/architecture.md) 为准。

本文中的“必须”和“不得”表示稳定约束。用户确认的 UI 调整改变这些约束时，代码、测试和本文必须在同一任务中对齐；发现三者冲突时不得静默沿用旧描述。

## 产品定位

cleancode 的 UI 是画布优先的本地开发工作台。

用户进入项目后应直接看到工作画布，并能通过分支工作区、终端积木和 Codex Agent 控制台完成真实本地开发活动。界面不得退化为营销欢迎页、文件管理器、聊天应用或完整 IDE。

## 信息架构

工作区是应用窗口唯一的顶层内容区域，并必须填满可用的窗口内容区。应用级入口可以作为窗口级控件叠加在工作区之上，但不得形成独立的常驻栏或占用工作区布局：

```txt
应用窗口
  ├─ 工作区：填满窗口内容区
  │   ├─ 左侧边栏：项目与分支工作区
  │   └─ 主工作区：积木画布
  │       ├─ 画布导航与操作
  │       ├─ 终端积木与终端组合
  │       └─ Codex Agent 控制台
  └─ 窗口级浮层：按内容宽度叠加，不形成独立常驻栏
      ├─ 主题设置入口
      └─ 应用通知
```

主画布必须占据窗口的主要面积。Codex Agent 控制台位于画布内，不得恢复为固定右侧栏。

窗口级设置与画布操作必须保持两层信息层级：应用设置位于窗口右上第一层，画布创建和组合操作位于其下方的第二层。后续应用级设置必须进入第一层，不得与画布操作混排；两层都必须按内容宽度占位，不得恢复为横跨窗口的标题栏。工作流发起动作属于终端对象，活动运行的状态和停止动作属于应用通知，不得混入第二层画布工具栏。应用通知从窗口右上角临时叠加，不占用工作区布局，并必须避让可操作的应用设置入口。

采用隐藏标题栏的平台必须只为原生窗口控件保留必要的局部安全区和窗口拖拽能力。该区域不得扩展为横跨窗口的常驻标题栏或全宽拖拽区，不得覆盖主画布的交互面或吞掉画布指针操作。

界面不得增加与当前开发工作无关的常驻区域，例如文件树、底部全局 Dock、营销式 Hero 或装饰性侧栏。新增长期区域前必须先确认它的用户目标和信息层级。

## 主题与外观

窗口右上第一层必须提供唯一的主题设置入口。入口不得占据工作区布局或形成常驻栏；默认状态必须低噪声但仍可发现，在悬停、键盘聚焦和打开状态下必须提供明确反馈。主题设置以不改变画布布局的右侧抽屉展示；抽屉打开时背景工作区不得继续接受交互，关闭后焦点必须回到入口。

主题偏好固定包含“系统”“浅色”和“深色”三种状态。首次使用默认为“系统”，用户选择必须跨应用重启恢复。选择“系统”时，有效主题必须跟随操作系统并响应运行中的系统主题变化；选择“浅色”或“深色”时，有效主题不得被系统变化覆盖。

主题必须覆盖主题设置入口、侧边栏、画布、终端积木、终端组合、Agent 控制台、小地图、菜单、表单、弹窗、提示和 xterm 内容。主题切换不得重建终端或 Agent 会话，也不得修改项目、工作区或画布业务状态。Agent xterm 已缓冲的原始真彩色输出必须保持为统一可读的主题外观，不得在切换后混合展示切换前后的明暗配色。同一 Agent PTY 运行期间，其终端源 palette 必须保持为首次附加时的主题；切换主题或离开再返回工作区时，新建的 xterm surface 必须恢复该源 palette，再通过统一视觉转换匹配当前应用主题，不得用当前主题冒充仍在运行的 PTY 源主题。

所有当前和后续 UI 必须通过统一语义颜色表达背景、表面、文字、边框、焦点和状态，不得在组件中建立绕过主题系统的独立配色。尚未提供的颜色预设、字体、圆角和密度选项不得以空分组、禁用项或占位内容出现在主题设置中。

## 分支工作区

分支工作区是用户理解项目开发状态的主要边界：

```txt
一个分支工作区 = 一个完整工作面
```

完整工作面包含该工作区的积木图、终端积木、终端会话和 Agent 会话。切换分支工作区时，这些内容必须一起切换，不得串用其他工作区的会话或画布状态。

默认工作区以 `main` 作为稳定工作区名称。`main` 可以绑定真实 Git 分支；绑定状态不得制造另一个并列的“默认工作区”条目。项目尚未初始化 Git 时，侧边栏必须以“Git 未初始化”替代虚假的分支名，并保留“默认工作区”身份；初始化后显示真实绑定分支。

Agent 对话以“项目 + 工作区 + 当前 Git 分支 + Agent 身份”为隔离范围。默认工作区名称保持为 `main` 时，检出不同真实 Git 分支仍然属于不同 Agent 对话；同一分支的不同 Agent 也不得串用对话。切回原分支必须为每个 Agent 恢复其已经持久化的对话绑定。

独立 worktree 是实现隔离的技术手段。UI 可以通过辅助信息表达工作区类型，但不得把 worktree 路径提升为主要用户概念。

归档分支工作区属于破坏性操作，必须二次确认并明确说明：归档会移除 worktree 目录但保留 Git 分支。归档当前工作区时还必须说明将先切回默认工作区。

如果真实 Git 状态表明 worktree 已锁定，确认框必须展示锁定原因、目录会被移除但 Git 分支会被保留，并把主操作明确命名为“解除锁并归档”。该确认只适用于当前看到的锁状态；锁原因变化后不得静默复用。脏工作树即使已锁定也必须拒绝归档，不得向用户提供强制删除入口。

## 左侧边栏

左侧边栏只承载项目和分支工作区导航，以及与它们直接相关的操作。

左侧边栏必须提供：

- 添加和移除项目。
- 项目列表与每个项目的分支工作区列表。
- 当前项目和当前分支工作区的明确选中状态。
- 创建、切换和归档分支工作区的入口。
- 在默认工作区选择或检出可用 Git 分支的入口。

项目名、分支名和工作目录等长文本必须安全截断或折行，不得撑破布局。工作区类型、当前状态和不可用原因必须通过文字、图标或辅助属性表达，不得只依赖颜色。

移除项目必须二次确认，并明确说明：该操作会从 cleancode 项目列表中移除项目并停止其终端和 Agent 会话，但不会删除本地项目目录或 Git 数据。

## 主画布

主画布是终端、终端组合和 Agent 控制台的空间工作面。

画布必须支持：

- 展示当前分支工作区的积木图。
- 创建、选择、多选、移动、调整大小和删除终端积木。
- 保存积木图、终端位置与大小，以及画布视口。
- 创建、选择、移动、折叠、展开和解散终端组合。
- 创建、展示、选择、重命名、移动、调整大小和移除 Codex Agent 控制台。
- 在重新进入工作面后恢复已经持久化的画布事实。

终端积木、终端组合和 Agent 控制台的整体选择只能由顶部标题区域触发；标题中的操作控件只执行自身动作，正文交互不得隐式选择整体。普通整体选择在三类对象之间必须互斥；终端多选只允许通过明确的多选操作形成。单击画布空白区域必须清除当前终端、终端组合和 Agent 的整体选择。终端积木和 Agent 控制台不要求预先选中，用户靠近任一角即可直接调整大小。终端正文必须允许选择和复制文本，正文内的文本拖选不得触发节点移动或画布平移；存在文本选区时复制快捷键只复制选区，没有选区时 `Ctrl+C` 必须保留终端中断语义。三类对象的选中状态必须以克制的虚线边界和低亮度覆盖层表达，不得依赖高亮实线或大面积强色。

Agent 整理终端布局时，只能移动本次工作流的精确终端作用域及完整包含它们的终端组合。布局以发起 Agent 的已保存位置为锚点，在其下方按依赖层级从左到右、同层从上到下稳定排列，并使用对象真实尺寸与固定留白避开发起 Agent、其他 Agent、无关终端和无关组合；不得移动 Agent 或把无关对象吸入布局。组合必须以完整外框作为视觉单元参与，不能与同批普通终端或其他组合重叠，排列后统一重算边界。

布局提交不得覆盖用户正在进行或已经先提交的拖动：普通终端以自身为保护单位，组合任一成员被用户移动时保护整个组合，其余未冲突目标仍可完成排列。只有实际发生布局变化时，画布才在新图完成投影且相关拖动保护结束后，对发起 Agent 与可见排列结果执行一次适应视图；幂等结果不改变视口，聚焦不改变现有选择，也不持久化为新的业务事实。

画布工具必须位于主工作区内，并与窗口级设置分层放置。没有当前项目或桌面运行时不可用时，依赖真实项目、文件系统、PTY 或 Agent 的操作必须禁用或展示明确空状态。

浏览器预览只能用于展示界面，不得伪造真实项目、终端或 Agent 能力。

## 小地图

小地图是画布的空间导航视图，不是内容预览器。

小地图必须：

- 用简化图形表达已经纳入导航的画布对象，包括终端积木、折叠终端组合和 Codex Agent 控制台。
- 展示当前画布视口，并支持缩放、适应画布、收起、展开和视口移动。
- 支持从可导航缩略对象定位到对应画布对象。
- 用克制的状态差异表达选中、悬停、运行和失败，不得让状态色替代对象身份。

展开的终端组合以成员终端作为主要导航对象，不额外强调组合外框；折叠的终端组合以一个组合缩略块表达，并保留成员摘要语义。

Codex Agent 控制台在小地图中只显示中性的空间占位和身份。小地图不得展示终端输出、Agent 对话、授权内容、完整属性或文件内容。

## 终端积木

终端积木是在画布上承载交互式本地终端会话的运行对象。

终端积木必须支持：

- 显示名称、描述和未启动、运行中、已退出、失败等会话状态。
- 配置并执行启动命令。
- 输入命令并显示标准输出和标准错误。
- 停止当前命令。
- 重开空终端会话。
- 编辑信息、调整大小和删除。

终端会话的工作目录必须来自当前分支工作区对应的本地目录。

终端主要操作应直接可发现，低频会话管理动作可以进入更多菜单。图标按钮必须提供可访问名称或工具提示；编辑表单必须提供明确标签、输入提示、保存和取消。

### 启动命令语义

未配置启动命令时，启动入口必须引导用户完成配置。已经配置时，执行启动命令必须：

1. 终止该终端的旧会话。
2. 启动新的终端会话。
3. 清空旧的可见输出。
4. 向新会话写入且只写入一次启动命令。

启动过程必须防止重复触发。启动命令不得写入仍在运行的旧项目进程。

### 重开空终端会话语义

重开空终端会话必须替换旧会话、清空旧输出，并且不得执行已配置的启动命令。入口文案或工具提示必须明确这一差异。

### 终端依赖工作流语义

终端积木通过输入、输出连接点建立有向依赖。连接和任务/服务执行配置随工作区保存；自连接、重复连接和会形成环的连接必须被拒绝。

本节只定义稳定的用户可见交互。上下文归属、执行计划、状态迁移、任务与服务语义、实现入口和验证矩阵统一维护在 [终端依赖工作流](../contexts/run/terminal-workflow.md)。

- “启动命令”仍只运行当前终端，不触发依赖级联。
- 工作流从终端上的“从此处运行流程”发起，只运行该终端及其后代；顶部工具栏不常驻全局运行入口。
- 工作流活动时，窗口右上角持续显示可关闭的活动通知，并提供“停止本次运行”；发起本次运行的根终端将“从此处运行流程”切换为同名兜底动作。顶部工具栏不展示运行状态或流程停止动作。同一工作区同一时间只允许一个活动工作流。
- 工作流状态独立于终端会话状态，使用等待、运行、就绪、成功、失败、阻塞和已停止表达任务进度。
- 任务终端可配置成功退出码和超时；服务终端可选择字面量输出或 TCP 端口作为就绪条件，并配置就绪超时。
- 多个根节点可以并行；汇合节点等待全部上游成功或就绪；失败只阻塞依赖该节点的后代。
- 折叠终端组合时隐藏成员之间的工作流连线，但不改变连接、计划或运行状态；组合本身不是工作流节点。
- 活动通知随同一个运行 ID 原地更新为就绪、成功、失败或已停止；停止请求进行中必须禁用重复提交。关闭活动通知不得停止工作流，普通状态更新不得将它重新打开，后续失败必须重新提示；切换工作区后再次加载同一运行的既有终态不得重复提示，返回仍在活动的运行时必须恢复活动通知与停止入口，运行在离开期间首次失败时必须提示一次；失败节点和连线仍保留失败或阻塞投影。

## 终端组合

终端组合是只允许终端成员加入的类型化组合。它用于组织和批量管理开发命令，本身不创建新的 PTY，也不承载终端输出。

终端组合必须遵守：

- 有效组合至少包含两个终端成员。
- 组合动作只能影响该组合的终端成员。
- 解散组合只移除组合关系，必须保留成员终端。
- 折叠和展开只改变展示形态，不得改变成员关系或运行状态。
- 组合成员的运行状态属于成员自身，不得在组合头部重复制造聚合状态。

用户必须能够创建组合、编辑名称、折叠或展开、添加或移出成员、启动成员启动命令、停止成员当前命令、重开成员终端会话和解散组合。

组合编辑模式必须明确表达当前选择、可加入成员、不可加入成员、拖入、移出以及可能导致组合解散的结果。少于两个有效成员时，系统必须阻止形成组合或自动解散组合。

常用组合操作应保持可发现并按运行、成员管理和结构管理形成清晰分组。具体图标、按钮形态和排列属于可演进的表现细节，不是本文的稳定契约。

## Codex Agent 控制台

Codex Agent 控制台是画布内的本地 Codex CLI 交互工作面。它采用节点式画布交互，但不是普通终端积木，也不属于终端组合。

Codex Agent 控制台必须：

- 在紧凑头部只显示稳定 Agent 名称；Codex CLI 身份和当前分支工作区不得作为重复副标题常驻展示。
- 在紧凑头部的 Agent 名称与更多菜单之间常驻显示“CleanCode MCP”图标开关；鼠标悬停或键盘聚焦时必须说明它只授予当前 Agent 查看和修改画布终端积木、组合、执行配置与依赖工作流的能力。
- 低频动作收纳在常驻可见的更多菜单入口中，不得依赖悬停后才显示。
- 支持双击 Agent 名称直接进行就地重命名。
- 承载真实 Codex CLI PTY 输入与输出。
- 支持选择、移动和调整大小。
- 在控制台内部滚动时只滚动 Agent 内容，不得触发外层画布缩放或平移。
- 展示并处理需要用户确认的 Agent 工具授权。
- 在 Agent 修改积木图后刷新当前工作面。
- 切换分支工作区时连接对应的 Agent 会话，不串用其他工作区状态。
- 完全退出并重新打开应用后，恢复当前项目、工作区和 Git 分支已经完成的 Codex 对话。
- 完全退出并重新打开应用后，恢复 Agent 数量、名称、位置和大小。
- 完全退出并重新打开应用后，恢复每个 Agent 独立的 CleanCode MCP 开关状态。

一个工作区允许拥有零个或多个 Codex Agent 控制台。新工作区首次进入时创建一个默认 Agent；用户移除最后一个 Agent 后必须保留空状态，不得静默重建。创建第二个及后续 Agent 时必须说明它们共享当前工作区目录、可能同时修改相同文件；需要文件级隔离时应使用不同 worktree 工作区。

每个 Agent 必须拥有稳定身份和独立的 Codex CLI PTY、输入输出、审批、MCP 会话及分支对话绑定。移动、选择、重命名或调整控制台大小不得重启或重复创建 Agent 会话。

CleanCode MCP 开关只控制 cleancode 内建画布 MCP。开启时，该 Server 必须成功初始化，其全部当前和未来工具在 Codex MCP 层默认预批准，不显示 Codex 原生工具审批；初始化失败时 Agent 会话必须展示异常，不得在缺少画布工具时静默继续。用户 Codex 的 sandbox、全局 approval policy，以及 Shell、文件、Git、网络和其他 MCP 的权限不得被顺带覆盖。切换运行中的 Agent 时必须重启该 Agent 的 PTY、继续原 Codex thread、释放旧 MCP 端点并取消旧待审批请求，不得影响其他 Agent；没有活动 PTY 时只保存期望状态并在下次附加时生效。删除画布对象、解散组合和断开终端依赖仍必须经过 cleancode 独立审批，不能因 Codex 原生预批准而绕过。

删除终端或解散组合的审批必须明确展示动作、目标名称、目标 ID、影响范围和保留/执行动作，不得只展示机器 ID。断开依赖的审批必须显示上游名称/ID、下游名称/ID、精确连接 ID，并说明只断开这一条依赖，保留两端终端、启动命令、执行配置和组合。审批出现时，画布必须用临时“审批意图连线”连接发起请求的 Agent 与目标对象，并为目标提供区别于普通选择态的审批高亮；折叠组合中的目标终端由组合节点作为可见代理并标明对应待处理内容。断开依赖时，展开端点高亮真实依赖边，折叠端点使用不可交互的临时代理边；两端位于同一折叠组合时不得画自环，只标明组合“包含待断开依赖”。这些投影不得持久化、参与选择、删除或重连。用户可以通过“在画布中查看”同时聚焦 Agent 与所有可见目标，但不得因此改写现有选择。批准后卡片保持执行中状态直到收到实际结果；拒绝、成功或会话取消后移除，执行失败时保留明确错误，目标已不存在时禁用破坏性动作并提示 AI 重新检查画布。多个请求按到达顺序展示，并提示剩余请求数量。

CleanCode MCP 开启时，用户未加限定地说“终端”“整理终端”“终端布局”“终端组合”“终端工作流”或“启动项目的终端组合”，Agent 必须优先理解为当前画布事实并先查看画布；为了确定启动命令可以随后读取仓库，但最终必须通过画布工具创建终端、配置 task/service、建立依赖与组合，排列精确相关终端，再检查工作流计划，不得用直接启动 Shell 进程或创建项目配置代替。当前 MCP 能搭建和检查工作流，但不能启动终端、组合或工作流，Agent 不得把“已搭建”表述为“已运行”。只有明确提到终端源码、Terminal 组件、xterm、PTY 或终端模块实现时，才理解为项目代码。关闭 MCP 时不得向原生 Codex 注入这层画布语义。

移除 Agent 属于破坏性操作，必须确认并明确说明：系统会停止该 Agent、取消其未完成审批并删除 cleancode 中的 Agent 定义和对话绑定，但不会回滚项目文件、删除 Git 提交或影响其他 Agent。

Agent 控制台不得展示终端端口，不得加入终端组合，也不得进入普通终端积木的创建、删除、组合或批量运行流程。

正常状态必须保持静默：Codex CLI 已安装且会话正常运行时，不得常驻展示“已安装”“已连接”、版本号或同义状态卡。只有运行时不可用、检查中、未检测到 CLI、会话失败或会话结束等需要注意的状态，才显示一条紧凑辅助提示。

对话恢复失败时必须提供紧凑的“重试”和“新对话”动作。新对话只替换当前项目、工作区、Git 分支和当前 Agent 的恢复绑定，不得删除其他 Agent 或其他分支的对话。

Agent 身份与工作区构成紧凑头部，异常提示属于次要信息，终端输出占据主要面积。正常状态不得使用大面积成功色；警示色只用于需要处理的异常或授权状态。

本地 Codex CLI 必须通过应用层用例操作项目、分支工作区、积木图和终端会话，不得直接修改 React 状态、持久化文件、数据库或 PTY 进程。

## 状态与反馈

界面必须明确表达选中、悬停、焦点、禁用、运行中、失败、空状态和进行中操作。

状态反馈必须遵守：

- 正常状态尽量静默，避免重复徽标、说明行和成功色卡片。
- 异常状态说明发生了什么，以及用户是否需要采取行动。
- 破坏性操作必须说明影响范围和可恢复性。
- 进行中操作必须防止重复提交或明确处理并发结果。
- 颜色只能辅助状态，不得成为唯一信息载体。
- 浏览器预览、桌面运行时不可用和真实桌面能力必须清楚区分。

应用级通知属于表现层易失状态，用于反馈已经发生或正在进行且不应占用常驻操作区域的事件。通知必须从窗口右上角弹出，支持信息、成功、警告、错误和活动语义，多条通知可以堆叠并分别关闭；同一事件可以原地更新内容和语义，也可以携带一个与事件作用域一致的上下文动作。异步动作进行中必须显示进行中文案、禁用重复提交，并在完成后恢复或随事件更新。错误通知默认保留到用户关闭，其他通知可以按事件需要自动关闭。通知关闭只移除界面反馈，不得修改事件所属上下文的业务状态、终端输出或诊断事实。通知不跨应用重启恢复，也不得替代节点、连线或对象自身需要长期保留的状态表达。

## 视觉与可访问性

工作台采用克制、低噪声、适合长期使用的桌面工具风格。

- 信息层级优先于装饰；主要工作内容必须获得最大视觉面积。
- 色彩优先服务于选中、警示、失败和运行状态，不得大面积铺设单一强调色。
- 控件密度应适合开发工作，临时编辑优先使用轻量浮层、弹出层或就地表单。
- 图标按钮必须有工具提示或等效可访问名称。
- 表单控件必须有标签；占位符不得替代标签。
- 文本、焦点和状态提示必须具备可辨识对比度。
- 不得用大面积渐变、装饰光斑或无意义插画承载核心界面。

## 关键验收不变量

- 用户进入项目后可以直接使用画布，而不是先经过营销或欢迎页面。
- 完全退出并重新打开应用后，恢复退出前的当前项目及该项目已提交的当前工作区；项目不可用时回退到首个可用项目。
- 分支工作区切换会同时切换积木图、终端和 Agent 工作面。
- 终端组合不会误操作非成员或非终端对象，解散不会删除成员终端。
- 多个 Agent 控制台保持独立画布节点语义，并与普通终端积木及终端组合隔离。
- Agent 整理工作流后，精确相关终端按依赖关系稳定落在发起 Agent 附近并避开无关对象；并发用户拖动优先，实际变化只触发一次适应视图且不改变选择。
- 小地图能够反映终端、折叠终端组合和 Agent 控制台的位置，但不泄露终端或 Agent 内容。
- 正常状态不重复占用视觉注意力，异常和破坏性结果能够被清楚理解。

## 维护规则

修改用户可见 UI 时必须判断本次变化属于哪一类：

1. 改变稳定产品语义或交互不变量：同步更新本文和对应行为测试。
2. 改变可演进的实现细节：更新代码与测试，不把临时样式追加为本文的永久规则。
3. 尚未确认或尚未实现的方向：记录到 [UI 路线图](ui-roadmap.md)，不得使用“必须”描述为当前能力。
4. 替换既有决策：删除或改写旧规则，不保留互相矛盾的新旧描述。

截图、参考图和一次性标注只能作为具体任务输入。除非明确标注状态、适用范围和替代关系，否则不得作为长期 UI 事实来源。
